## 6. Ranked confirmed local work

### Priority A - claims-control package

#### CTL-01 - Claims check adjacent text rather than the property

**Affected:** `docs/claims.json`, `scripts/verify-record-claims.py`,
`scripts/test-verify-record-claims.py`

Confirmed false-green paths:

1. A real alternate cap,
   `if (store.events.length > 200) store.events.length = 200`, passes.
2. Predictable token generation passes if `randomUUID()` or old call text
   remains elsewhere in the file.
3. An unrelated `toHaveLength(205)` satisfies the timeline-test claim.
4. A lightweight tag satisfies a claim requiring an annotated tag.
5. Whole-file config/test greps do not prove binding to the claimed symbol.

**Consequence:** CI can certify a security or audit property when only
neighboring text remains.

**Required direction:**

- Execute event retention: append more than 200 distinct events and prove all
  remain.
- Test the exact capability generator's behavior or data flow.
- Check tag object type, peeled target, and any claimed annotation property.
- Execute or semantically parse the exact configuration/test property.

**Acceptance:** preserve matching text while breaking the property; every
mutation must fail and name its claim. Run a separate clean null arm.

#### CTL-02 - Deleting one claim restores green

Removing one manifest entry reduces coverage from 15 to 14 and exits 0. The
harness enumerates only the claims that remain.

**Required direction:**

- Compare candidate claim IDs with an authoritative base.
- Require an explicit reviewed retirement record for removals.
- Do not rely only on a count floor; replacement preserves the count.
- Do not rely only on an in-repository digest; the candidate can regenerate it.
- Treat the result as partial until OBL-30 supplies an external trust anchor.

**Acceptance:** removing or replacing a required claim without authorized
retirement fails and names the missing ID.

#### CTL-03 - Claims negative controls do not run in CI

`scripts/test-verify-record-claims.py` appears in no workflow. CI runs the
normal verifier but not its mutation harness.

**Required direction:** wire the harness, or an equally discriminating reduced

**Boundary:** candidate-controlled wiring does not close OBL-30.

### Priority B - lifecycle and Founder authority

These can occur in one Node process because `await` yields to another request.
They are not merely future database concerns.

#### LIFE-01 - Founder decision compare-and-set is not atomic

**Affected:** `lib/dev-hq/adapters/dev-approval-manager.ts`,
`types/contracts/approval-manager.ts`,
`lib/dev-hq/founder-request-service.ts`

`recordDecisionIntent`, `recordContinuation`, and
`decidePendingApproval` await a read and later spread/save stale whole records.
Concurrent approve/reject requests can both observe no decision. A stale
continuation save can reopen a terminal approval.

**Acceptance:** barrier-controlled approve/reject and fast-continuation races
leave one immutable decision, one matching continuation payload, and no
terminal-to-pending transition.

#### LIFE-02 - Concurrent executive review can create duplicate approvals

The service performs `findPendingByExecution`, crosses several awaits, and
creates a fresh random-ID approval. Two callbacks can both pass the absence
check.

**Acceptance:** N simultaneous callbacks return one stable approval ID and the
store contains exactly one approval for the execution.

#### LIFE-03 - A losing review callback can contaminate the winner

Findings and evidence are written before the guarded outcome transition.
Different callbacks can both observe `pending`; the loser can attach blocking
findings to a review the winner resolved as passed.

**Acceptance:** race pass/no-findings against
changes-requested/blocking-findings. Only the winner's payload may appear in
review, evidence, or timeline state.

#### LIFE-04 - A fast Trigger callback can reopen terminal state

After `tasks.trigger()` returns, submission unconditionally marks the execution
running and resets the run to `founder_request_received`. A worker that
finalizes before the response returns can be rolled back.

**Acceptance:** a fake Trigger platform finalizes before returning its handle;
the final execution/run remain terminal while run identity and lineage are
recorded.

#### LIFE-05 - Concurrent finalization creates false audit history

Two calls can pass the initial terminal check. The second can emit a false
task-status-refused record, and completion events are not all deduplicated.

**Acceptance:** concurrent identical finalizations produce one task
transition, no refusal, and one completion event.

**Priority:** blockers before production and high-severity current local risks.
They need not block the isolated claims-control fix, but Phase 1 cannot finish
with them open.

### Priority C - major local/API correctness

#### API-01 - Founder submission leaves partial, duplicate-prone state

`createFounderRequest` creates project, task, execution, run, and event records
before Trigger dispatch. If Trigger accepts but its response is lost, or throws
without a conclusive answer, the route reports failure while partial state
remains. Retry has no stable submission identity.

**Acceptance:** simulate "accepted, then response lost"; retry the same request
identity and prove one project/task/execution/event lineage and one converged
dispatch.

#### API-02 - Internal validation and error mapping are inconsistent

Six routes use raw `request.json()` and commonly return internal exception
messages as 500 responses. Other routes cast parsed JSON without requiring a
plain object, so valid JSON `null` can become a 500. Dispatch silently treats
wrong-type optional fields, including `idempotencyKey`, as absent.

**Acceptance:** every route rejects invalid syntax, `null`, arrays, wrong
required types, and present-but-invalid optional fields with a stable 4xx and
no side effects; unexpected failures return a fixed non-leaking 500.

#### EXEC-01 - Legacy execution port bypasses one-live-execution

The exported legacy `assignExecution` path creates routed work without the
shared live-execution guard. No current production service calls it, so it is
latent but exposed.

**Acceptance:** remove the unused surface or route it through the same atomic
invariant; concurrent attempts for one task never leave two live executions.

#### UI-01 - Audit panel falsely says evidence storage/API do not exist

`components/mission-control/AuditTrailPanel.tsx` says Evidence has no store,
repository, or API. Evidence is stored, has an adapter, and is included in
browser state.

**Acceptance:** render available evidence or state accurately that the panel
does not yet present it.

#### DOC-01 - Current progress report is stale

`docs/governance/CURRENT_PROGRESS_UPDATE.md` names `b32caec` as HEAD, reports
848 tests, and describes a documentation-only candidate. Refresh it only after

## 8. Required three-loop procedure

Each batch receives at most three implementation/review loops. Three loops are
not permission to self-approve.

### One loop

1. **Implement**
   - Re-read the finding, ADR/standard, and acceptance criteria.
   - Make the smallest scoped change.
   - Do not combine architectural redesign with a local fix.

2. **Prove**
   - Run a clean null arm.
   - Reproduce the exact known-bad behavior.
   - For controls, preserve matching text while breaking the property.
   - For concurrency, force the dangerous schedule with barriers.
   - Restore the candidate and run focused plus full regression validation.

3. **Review**
   - Independent Code Reviewer checks implementation, errors, tests, and
     discrimination.
   - Architecture Reviewer checks authority, atomicity, lifecycle invariants,
     ADR consistency, and durable-adapter requirements.

4. **Correct**
   - Repeat against every confirmed blocker.
   - After three unsuccessful loops, stop changing that batch, record the
     defect/evidence, and defer it as an isolated package.

### Prohibited shortcuts

- Passing the existing suite without a new red arm.
- Grepping for a function name when the claim is behavioral.
- Running mutations against an already-red baseline.
- Letting the author supply the only negative control.
- Calling an in-repository digest independent approval.
- Treating local-only tags/settings as repository state.
- Treating a mocked Trigger call as live WebSocket proof.
